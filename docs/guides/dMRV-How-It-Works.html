0 ภาพรวมระบบ (Big Picture)

Carbon Ready คือระบบ "ดิจิทัล MRV" สำหรับโครงการพลังงานสะอาด (เช่น โซลาร์รูฟท็อป) ที่ทำให้กระบวนการ วัด → รายงาน → ตรวจสอบ → ออกใบรับรอง มีหลักฐานครบ ตรวจย้อนได้ และป้องกันการแก้ไขข้อมูลย้อนหลัง

ลองนึกภาพง่าย ๆ ว่าระบบทำ 4 อย่างหลัก:

📊 วัดและคำนวณ

รับข้อมูลการผลิตไฟฟ้า (kWh) แล้วคูณกับ "ค่าการปล่อยคาร์บอนของกริด" (Emission Factor) เพื่อหาว่าช่วยลดคาร์บอนได้กี่ตัน (tCO₂e)

✅ ตรวจสอบและรับรอง

ผู้ตรวจสอบ (Verifier) ดูหลักฐานประกอบ แล้วอนุมัติ / ขอแก้ไข / ปฏิเสธ ผ่านขั้นตอนที่ควบคุมด้วย state machine

🔗 ออกใบรับรอง + Anchor

เมื่ออนุมัติแล้ว ระบบออก Verifiable Credential (VC) และ Anchor ขึ้น Hedera Guardian (ปัจจุบันจำลอง)

🛡️ ตรวจย้อนหลังไม่ได้แอบแก้

ทุกการกระทำถูกบันทึกใน Audit Log ที่ผูกกันด้วย Hash Chain — ถ้ามีใครแก้ข้อมูล ระบบจะตรวจจับได้ทันที

หมายเหตุ: ใน MVP นี้ ข้อมูลทั้งหมดเก็บใน localStorage ของเบราว์เซอร์ และการเชื่อม Hedera Guardian เป็นการจำลอง (simulated) โดยออกแบบให้สลับไปต่อ Backend/Blockchain จริงได้โดยไม่ต้องแก้ UI

1 ผู้ใช้งานและบทบาท

ระบบออกแบบรอบ 4 บทบาทหลัก แต่ละบทบาทรับผิดชอบคนละช่วงของกระบวนการ

3 ขั้นที่ 1 — บันทึกข้อมูลการผลิต (Monitoring)

หน้า /projects และ /upload · ผู้ทำหลัก: Project Owner

  1. Project Owner
    สร้างโครงการ — ระบุชื่อ, ที่ตั้ง, กำลังติดตั้ง (kWp), วันที่ Commission เช่น "Pune Rooftop Phase 1 — อินเดีย — 250 kWp" ระบบจะ map ที่ตั้ง → ประเทศ เพื่อใช้เลือก Emission Factor ภายหลัง
  2. Project Owner
    อัปโหลดไฟล์ CSV รูปแบบ Date,Generation_kWh (เช่นข้อมูลรายวัน ธ.ค. 2025 – พ.ค. 2026)
  3. System
    ตรวจสอบทีละแถว — ปฏิเสธแถวที่ผิดพลาดอัตโนมัติ:
    วันที่ซ้ำ ค่าติดลบ รูปแบบวันที่ผิด หัวคอลัมน์ไม่ครบ แถวที่ผ่าน → บันทึก
  4. System
    บันทึกข้อมูลที่ผ่าน ลงตาราง monitoring_records และเขียน Audit Log: CSV_UPLOADED

4 ขั้นที่ 2 — คำนวณคาร์บอน (Reporting)

หน้า /emission-factors และ /calculations · ผู้ทำหลัก: ESG Manager

  1. ESG Manager
    ตั้งค่า Emission Factor — ค่าความเข้มข้นคาร์บอนของกริดไฟฟ้าแต่ละประเทศ (เช่น อินเดีย 0.79 kgCO₂e/kWh) ระบบเก็บแบบมีเวอร์ชัน — แต่ละคู่ (ประเทศ, แหล่ง) มีค่า "ปัจจุบัน" (is_current) ได้แค่หนึ่งค่า ค่าก่อนหน้าถูกเก็บเป็นประวัติ
  2. ESG Manager
    สั่งคำนวณ — เลือกโครงการ ระบบจับคู่ Emission Factor ที่มีผล ณ วันนั้นโดยอัตโนมัติ
  3. System
    คำนวณการลดคาร์บอน ด้วยสูตร:
    การลดคาร์บอน = ปริมาณไฟที่ผลิต (kWh) × Emission Factor (kgCO₂e/kWh)
    เช่น 30,000 kWh × 0.79 ≈ 23,700 kgCO₂e ≈ 23.7 tCO₂e
    แล้วสรุปออกเป็น รายวัน / รายเดือน / รวมทั้งหมด พร้อมกราฟแนวโน้มรายเดือน
  4. System
    บันทึกผลลง calculation_results และเขียน Audit Log: CALCULATION_EXECUTED

5 ขั้นที่ 3 — รวบรวมหลักฐาน (Evidence)

หน้า /projects/:id → แท็บ Evidence · ผู้ทำหลัก: Project Owner

  1. Project Owner
    อัปโหลดเอกสารประกอบ (PDF / JPG / PNG / XLSX, ไม่เกิน 50 MB) เช่น ใบอ่านมิเตอร์, บิลค่าไฟ, รายงาน Commissioning, รูปหน้างาน, log จาก SCADA ของอินเวอร์เตอร์
  2. System
    เดาหมวดหมู่อัตโนมัติ จากชื่อไฟล์ (ผู้ใช้ปรับได้) — มี 7 หมวด:
    meter_readingutility_billcommissioning_reportsite_photomaintenance_reportsupporting_evidenceverification_report
  3. System
    จัดเก็บแบบมีเวอร์ชัน — ไฟล์แรกเป็น v1 (active) ถ้าอัปโหลดแทนที่ จะได้ v2 และ v1 ถูกทำเครื่องหมาย superseded (ผูกกันด้วย parent_id) แต่ละไฟล์มี content_hash เพื่อตรวจการแก้ไข
  4. Project Owner
    สามารถ Archive (ซ่อนจากรายการหลักแต่เก็บประวัติไว้) ได้ และเมื่อแพ็กเกจถูกอนุมัติแล้ว หลักฐานทั้งหมดจะถูก ล็อกเป็น read-only

6 ขั้นที่ 4 — ตรวจสอบและรับรอง (Verification)

หน้า /verifications และ /verifications/:id · ผู้ทำหลัก: Verifier

State Machine ของแพ็กเกจตรวจสอบ

draft→ submitted→ under_review→ approved 🔒
จาก under_review ยังแยกไปได้: revision_required rejected
  1. Project Owner
    ส่งแพ็กเกจขอรับรอง (VerificationRequest) ที่ผูกช่วงเวลา, ตัวเลขการลดคาร์บอน, snapshot ของ factor, และรายการหลักฐาน → state เป็น submitted
  2. Verifier
    เปิดคิวงาน ที่ /verifications เห็น KPI (จำนวนงานค้าง, ตัวจับเวลา SLA, อัตราขอแก้ไข, จำนวนอนุมัติ) แล้วกดเข้าแพ็กเกจ → state เป็น under_review
  3. Verifier
    ตรวจความครบของหลักฐาน ตามหมวดที่กำหนด (required_categories) อ่านเอกสาร และแสดงความเห็นแบบเธรด (ตอบกลับกันได้ ระบุได้ว่าคอมเมนต์ระดับแพ็กเกจหรือระดับไฟล์)
  4. Verifier
    ตัดสินผล 1 ใน 3 ทาง:
    การกระทำผลลัพธ์
    อนุมัติ (Approve & Lock)state → approved, คำนวณ hash_value ของแพ็กเกจ, ล็อกหลักฐานเป็น read-only, บันทึก locked_at · Audit: VERIFICATION_APPROVED
    ขอแก้ไข (Request Revision)state → revision_required ส่งกลับให้ Owner แก้แล้วส่งใหม่ · Audit: REVISION_REQUESTED
    ปฏิเสธ (Reject)state → rejected (สิ้นสุด) · Audit: VERIFICATION_REJECTED

7 ขั้นที่ 5 — Anchor ขึ้น Hedera Guardian

หน้า /verifications/:id และ /guardian · ผู้ทำหลัก: Verifier จำลอง (Sprint 3)

  1. System
    เมื่อแพ็กเกจ approved แล้ว จะขึ้นแบนเนอร์ "🔒 รอ Anchor — Hedera Guardian" และมีปุ่ม "Anchor to Hedera Guardian" ปรากฏ
  2. Verifier
    กดปุ่ม Anchor ระบบสร้าง Verifiable Credential (VC) แบบจำลองตามสคีมา MRV_APPROVAL_SCHEMA_V1 (มาตรฐาน W3C VC, 10 properties)
  3. System
    ออกใบรับรองโดยมีข้อมูล (สร้างแบบ deterministic จาก hash):
    ฟิลด์ตัวอย่าง
    Credential IDurn:vc:vr1001…
    Issuer DIDdid:hedera:testnet:CarbonReadyIssuer…
    HCS Topic / Sequence0.0.480100 / #2
    Explorer (HashScan)hashscan.io/testnet/topic/…/message/2
    แล้วเขียนกลับลงแพ็กเกจ: credential_id, anchored_at, hcs_topic_id, hcs_sequence_number · Audit: VERIFICATION_ANCHORED
  4. Verifier
    ตรวจ Credential Registry ที่ /guardian (แท็บ Registry) เห็นรายการ VC ทั้งหมดที่ Anchor แล้ว พร้อมลิงก์ HashScan (จำลอง) — แท็บ Schema แสดงโครงสร้างสคีมาที่ใช้
จำลอง vs ของจริง: ปัจจุบันยังไม่ได้ต่อ Hedera SDK / Guardian REST จริง — ไฟล์ lib/guardian.ts สร้าง VC จำลองที่มี sequence number และ URL แบบกำหนดได้ เมื่อจะใช้งานจริง เพียงสลับไฟล์นี้เป็นไคลเอนต์ Guardian จริง โดย UI ไม่ต้องแก้

8 ขั้นที่ 6 — Audit Trail (Hash Chain)

หน้า /audit-log · ผู้ทำหลัก: Auditor · ทำงานเบื้องหลังตลอดทุกขั้น

หัวใจของความน่าเชื่อถือ: ทุกการกระทำในระบบ (อัปโหลด, คำนวณ, อนุมัติ, anchor ฯลฯ) ถูกผนวกเข้า Audit Log แบบ append-only และแต่ละแถวผูกกับแถวก่อนหน้าด้วย Hash:

row_hash = hash( prev_row_hash + canonical(ข้อมูลหลักของแถวนี้) )

เหมือนการ "ร้อยลูกโซ่" — ถ้ามีใครแก้แถวใดแถวหนึ่งย้อนหลัง ค่า hash ของแถวนั้นและทุกแถวหลังจากนั้นจะไม่ตรงกัน

  1. Auditor
    เปิดหน้า /audit-log ระบบคำนวณลูกโซ่ใหม่ทั้งหมดตอนโหลด แล้วแสดงแบนเนอร์ผล:
    ✓ Hash chain verified · N rows  หรือ  ✗ Hash chain broken · ตรวจพบการแก้ไขหลังแถวที่ N
  2. Auditor
    กรองและตรวจสอบตาม action / entity / ช่วงวันที่ แต่ละแถวแสดงผู้ทำ, การกระทำ, ข้อมูล ก่อน → หลัง (diff) และค่า row_hash
